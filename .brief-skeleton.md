Build the project skeleton for Free Agents. Read MISSION.md and CLAUDE.md in
the repository root first: they are the governing documents and they are
authoritative over anything in this brief. They are gitignored on purpose (they
live in a private repository) so do not commit them and do not remove them from
.gitignore.

You are laying a foundation, not building features. Every later task inherits
the shape you choose here, so the structure matters more than the amount of
code. Prefer fewer, well-placed files over a large scaffold.

## Stack

TypeScript on Node 22. Express for HTTP. Postgres via Prisma. Vitest for tests.
ESLint and tsc for static checks. npm, not pnpm or yarn.

## The one architectural rule that matters

Nothing in src/domain may import an ArcBlock package, or any vendor SDK at all.
Domain code calls interfaces defined in src/adapters, and an adapter
implementation is the only file that ever knows a vendor exists. This is
invariant 9 in MISSION.md, portability, and it is the thing most likely to be
quietly violated later. Make the structure enforce it: define the interfaces as
TypeScript types in src/adapters/<capability>/types.ts, and put the
implementation in src/adapters/<capability>/arcblock.ts behind a factory
function.

Adapters needed, interfaces only for now, with in-memory or stub
implementations that satisfy the types and throw a clear "not implemented"
error where real work is required:

- identity: create an operator DID, create an agent DID delegated from an
  operator DID, resolve a DID, sign and verify with a DID key
- credentials: issue a work-history credential, verify one, serve one
- github: read-only client for reading a pull request, its merge commit, and
  its signature verification status, plus fork-and-open-PR. It must be
  impossible to write to a repository other than through fork and pull request
- storage: nothing ArcBlock-specific, this is plain Prisma, so no adapter

## Domain model

Write the Prisma schema and the domain types for these entities. Read
MISSION.md sections "The hire loop" and "Core capabilities" for the real
semantics, and follow them exactly rather than inventing your own.

- Operator: DID, GitHub login, created date
- Agent: DID, owning operator, name, skills, GitHub login, proof status
- Job: buyer, agent, target repository, brief hash, confirmed spec hash,
  state, job id used as the PR trailer
- Credential: the issued VC, the job it came from, issue date, subject agent
- Review: author, agent, rating, text, and the completed job that authorizes it

Job state is a state machine and should be modelled as one, not as a loose
string. The states follow the hire loop in MISSION.md. A review row must be
impossible to create without a completed job by that buyer against that agent,
and the schema should express that with a foreign key rather than leaving it to
application code.

## What to actually build

1. package.json with the exact scripts MISSION.md gate 1 names: typecheck,
   lint, test. Plus dev and build.
2. tsconfig, eslint config, vitest config, prettier if you want it.
3. prisma/schema.prisma with the model above.
4. src/domain with the entity types and the job state machine, pure functions,
   no I/O.
5. src/adapters with the interfaces and stub implementations described above.
6. src/api with an Express app, a health endpoint, and route stubs for the hire
   loop. Routes may return 501 for now.
7. tests/ mirroring src/, with real tests for the job state machine and a test
   that asserts no file under src/domain imports from an adapter
   implementation or a vendor package. That last test is the structural
   guarantee, so make it real: read the files and check the imports.
8. .env.example with generic placeholder values, never real ones.
9. A short README section describing how to run it. Keep the existing README
   content, add to it.

## What NOT to build

No website, no UI, no styling. That is a separate track and a different model.
No real ArcBlock integration yet, interfaces and stubs only. No authentication
implementation. No payment anything.

## Constraints

- This repository is PUBLIC. No absolute paths, no machine names, no usernames,
  no IP addresses, no personal names, in code or in commit messages.
- Configuration comes from environment variables with generic defaults.
- No em dashes anywhere, including code comments and commit messages. This is a
  hard house rule. Use commas, colons, or separate sentences.
- Comments explain why, not what.

## Definition of done for this task

All three of these must pass, and you should run them:

    npm run typecheck
    npm run lint
    npm test

Commit on a branch named task/skeleton. Do not merge it and do not push.
