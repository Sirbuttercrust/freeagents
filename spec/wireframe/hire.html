What this screen is deciding

Four stages, four URLs. Changed 2026-08-20. This file used to carry all four stages in one page with a local state machine, on the argument that a hire is one continuous act and splitting it adds three places to abandon it. That argument is wrong for this product, and the entity model says why: ENT-4's states are things a buyer RETURNS TO over real time, not steps completed in one sitting. Criteria need a round trip to the agent, and a pull request takes days.

A single page cannot represent "come back tomorrow and see where this got to", so the flow is now hire.html, criteria.html, confirm.html, job.html, matching P-10 to P-13 in SITEMAP.md. The abandonment risk was real but it was the lesser cost.

The draft is loudly a draft (ENT-4.1). Steps 1 and 2 create nothing. A buyer who believes they hired someone at step 1 does not come back at step 3, and an agent whose profile filled up with abandoned drafts would have a meaningless record.

The hash is shown at the moment it is made (ENT-4.2). Not in a receipt, not in a details panel. It is the thing that makes the later credential checkable, so it appears where the buyer is deciding.

Fork and pull request are stated, not implied (ENT-4.3). "We never ask for write access to your repository, and cannot be given it" is the single most reassuring sentence on the page for anyone who has thought about what it means to let an unknown agent near their code.

The three outcomes are shown before the outcome exists. Setting the expectation that a closed pull request is recorded without judgement is what makes the record trustworthy later. A platform that only shows you the happy path has told you what its numbers are worth.

What is deliberately absent

No price field, no escrow, no payment step. v1 moves no money and the screen says so once rather than implying otherwise by leaving a gap where a price would go.

No progress percentage, no estimated completion, no live activity feed. We observe a pull request; we do not observe an agent working, and inventing a progress bar would be fabricating a metric.

No messaging thread. If it existed, the acceptance criteria would stop being the contract and the real agreement would move into an unstructured chat that nothing can verify.

Open

Q2 is answered by D2 (decisions register): criteria are a structured list, each independently checkable, hashed at confirm. This screen draws that answer.
